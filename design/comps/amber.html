Anchor durability under concurrent edits

edited 14:32 · 1,840 words · 4 backlinks · 2 anchors

Line numbers are the weakest possible anchor. Any edit above the target shifts them, and an external editor invalidates them silently. The durable representation has to be derived from content, with position kept only as a hint.

A code anchor stores a 64-character prefix, the exact span, and a 64-character suffix. Resolution tries exact hash, then hunk-mapping through the last [[checkpoint]], then unique search, then fuzzy match — each step downgrades confidence.

⌁ wb-01J2 · supports → anchors/resolve.rs:41–63

Hunk mapping

Because every task snapshots the workspace, we usually hold the file's bytes from the moment the anchor was created. Diffing that snapshot against the current file translates old offsets through the hunk list — near-exact, and cheap.

fn resolve(anchor: &Anchor) -> Resolution {
    if anchor.file_hash == current { return Exact(anchor.hint) }
    hunk_map(snapshot_at(anchor.created), current)
}

Fuzzy matching stays a last resort: duplicated text must resolve as stale, never as a confidently wrong match.
